Stop-and-Wait ARQ Protocol & Packet Optimization Mechanics

Understanding why there exists an optimal packet size $L^*$ and how Bit Error Rate (BER) shifts this equilibrium.

Force 1: Protocol Header Overhead

Small Packets $\implies$ Low Efficiency

Every frame carries a fixed header ($H = 40$ bytes: IP + TCP). When the payload $L$ is small, header overhead dominates:

Efficiency = \frac{L}{L + H}

For example, with $L = 64$ bytes, efficiency is only $64 / 104 \approx 61.5\%$. Even worse, Stop-and-Wait protocol requires an ACK round-trip delay ($2 \times t_{prop}$) for every single 64-byte frame, leaving the channel idle 99% of the time.

Force 2: Bit Error Vulnerability

Large Packets $\implies$ High Frame Loss

A frame of size $F = L + H$ bytes ($8F$ bits) is corrupted if even a single bit flips. Given independent bit errors with probability $\text{BER}$:

P_{err} = 1 - (1 - \text{BER})^{8(L + H)}

As $L$ increases, $P_{err}$ approaches $100\%$. In Stop-and-Wait ARQ, a corrupted packet forces a timeout of duration $t_{timeout}$, triggering retransmissions that destroy goodput.

The Synthesis

The Fundamental Trade-off ($L^*$)

The effective Goodput $G(L)$ is given by the delivered useful bits divided by the expected time per frame:

Goodput(L) = \frac{8L}{E[\text{Time per frame}]} = \frac{8L \cdot (1 - P_{err})}{RTT + P_{err} \cdot t_{timeout}}

Differentiating with respect to $L$ yields an optimal payload size $L^*$:

  • BER = 0: $L^* \to \infty$ (Make packets as large as MTU allows, e.g. 8192 B).
  • BER > 0: As channel noise increases, $L^*$ shifts downward to minimize frame error probability!
